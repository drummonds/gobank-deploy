How the deployment fits together

One environment (prod, preprod, demo, …) is one Hetzner Cloud server running PostgreSQL and the Model Bank demo. gobank-deploy creates it, puts a release on it, reports on it and deletes it. Creating a server is an explicit act; deleting it is what stops billing.

How a version reaches an environment

The code lives on the Forgejo at git.bytestone.uk. Releasing gobank there is the build stage: goreleaser attaches the demo binaries to the release, and hydrogen, the gokrazy appliance, which cannot build, fetches them into its store before a deploy. The laptop builds the demo from its own checkout and can push a build to hydrogen by hand. Either deploys to a server.

What the orchestrator talks to

From either place it runs: the same Hetzner project and the Route 53 zone, with secrets from Bitwarden.

Networking and firewalls

Every server is on the private network gobank (10.128.0.0/16) and has a firewall of its own name. The firewalls filter the public interface only: ssh and the demo from the admitted ranges (-admit, home), ping from anywhere. A loader reaches a demo over the private network, unfiltered. The rules are set on every up.

What up does

The same sequence for Create and Redeploy; only the create box starts billing. The release is built from the checkout on the laptop, or taken from the store here; the version the server then reports is what the environments page compares against what the next up would deploy.

The demo workflow

"Remove after" on a Create form makes a temporary environment: a gobank-workflow pipeline instance keyed by environment and expiry, created with the expiry as a label on the server, served until then, removed. Every minute the page starts the workflow for any temporary server nobody is looking after, so a restart does not leave one billing.

The Workflows page is the engine's view of all three workflows: each definition's steps and code, with its instances in every state, each instance leading to its steps as they ran.

The drill workflow

"Drill" on an environment's row runs gobank's upgrade drill (ADR-0003) as a pipeline instance keyed by environment, the two releases and the date: a day long enough to upgrade inside, then upgrade to the newest release, roll back, forward again. The demo is observed at /about.json before and after every hop and each hop is gated on the version serving, a clean previous stop with a known downtime, an intact handover and the same day as before. Every drill and its observations are kept in this program's database; the Drills page is the history, the DB Explorer the tables.

The perf workflow

"Measure" on the environments page runs gobank's performance run as a pipeline instance keyed by environment, scale and date: a fresh environment at the scale, the demo set flat out, customers added for ten minutes and days run for ten, the two rates read off /about.json — customers added per second and account days per 12h — then the server removed. The Performance page is the history, each run with its line for gobank's benchmark.md.

The load workflow

A fresh target at a scale with its books filled, a loader beside it on the private network, the customer journey — login, accounts, one account — walked up a ladder of concurrent users, ten journeys each, until a screen's p95 is over 2s; both boxes removed. The climb is on the Load tests page.

The scenario workflow

gobank-deploy scenario seven-years runs a scenario — a named configuration driven through timed steps on a fresh environment — as a pipeline instance keyed by environment, scale and date: create, add (the customers, flat out), years (flat out until the bank's day is the years on), wallclock (the day length set to real time and the bank following the clock), probe (the dashboard, the customer search by name and a customer's page, from outside at concurrency 1 and 4), remove. Each step is recorded with its figures and the run becomes a page of the Journal, the notebook kept in the repository's journal/ folder for the operator to annotate. It is the instrument for gobank's milestone 1: the capacity of one synchronous system over seven years.

The scan workflow

gobank-deploy scan <env> is a full performance scan of an environment as it stands, keyed by environment and date: survey (the environment must be serving; where the scan is), scan (every route the demo's /v1/openapi.json lists that the scan can drive — a GET without path parameters as the operator or as a customer by what the route needs, the customer search by its post — loaded at each rung of the concurrency ladder, 1, 4 and 16; the rest listed as not scanned with why). No server is made or removed. The scan is a run of the Journal like a scenario, and it writes the measured document, api/measured.json in gobank's checkout, so gobank's API pages show what each route measured alongside its facts.
